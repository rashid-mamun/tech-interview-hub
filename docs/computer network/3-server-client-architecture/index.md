# Client-Server Model and Architecture

## 17. What is the Client-Server model?
**Client-Server Model** হলো এমন একটি ডিস্ট্রিবিউটেড কম্পিউটিং স্ট্রাকচার, যেখানে কাজের দায়িত্বগুলো প্রোভাইডার (সার্ভার) এবং রিকোয়েস্টার (ক্লায়েন্ট) এর মধ্যে ভাগ করা থাকে। 
- **ক্লায়েন্ট** হলো ইউজারের ডিভাইস বা ব্রাউজার, যে কোনো সার্ভিস বা ডেটার জন্য রিকোয়েস্ট পাঠায়।
- **সার্ভার** হলো একটি শক্তিশালী কম্পিউটার প্রোগ্রাম বা ডেডিকেটেড হার্ডওয়্যার, যা ক্লায়েন্টের রিকোয়েস্ট প্রসেস করে এবং প্রয়োজনীয় ডেটা রেসপন্স হিসেবে ফেরত পাঠায়।

### How does the peer-to-peer model differ from client-server?
- **Client-Server:** এখানে একটি কেন্দ্রীয় সার্ভার থাকে এবং সমস্ত ডেটা ও ক্ষমতার নিয়ন্ত্রণ সার্ভারের কাছে থাকে। সার্ভার অফলাইন হয়ে গেলে সার্ভিস বন্ধ হয়ে যায়।
- **Peer-to-Peer (P2P):** এখানে কোনো কেন্দ্রীয় সার্ভার থাকে না। নেটওয়ার্কে যুক্ত প্রতিটি ডিভাইস (Node বা Peer) একই সাথে ক্লায়েন্ট এবং সার্ভার হিসেবে কাজ করে। যেমন: BitTorrent। একটি নোড অফলাইন হলেও অন্য নোড থেকে ডেটা পাওয়া যায়।

### What are the trade-offs between thin and thick clients?
- **Thin Client:** এটি ডেটা প্রসেসিংয়ের জন্য পুরোপুরি সার্ভারের ওপর নির্ভরশীল (যেমন ওয়েব ব্রাউজার)। সুবিধা হলো এটি যেকোনো কম দামি ডিভাইসে চলে এবং আপডেট সার্ভারেই হয়ে যায়। অসুবিধা হলো সার্ভার বা ইন্টারনেট ডাউন থাকলে এটি অকেজো।
- **Thick (Fat) Client:** এর নিজস্ব কম্পিউটিং পাওয়ার এবং ডেটা প্রসেসিং ক্ষমতা থাকে (যেমন একটি ডেক্সটপ অ্যাপ্লিকেশন)। ইন্টারনেট ছাড়াই এর আংশিক কাজ চলতে পারে এবং পারফরম্যান্স ফাস্ট হয়। তবে এটি ইনস্টল এবং মেইনটেইন করা বেশ জটিল।

## 18. What are the differences between Client and Server in web applications?
ওয়েব অ্যাপ্লিকেশনে ক্লায়েন্ট এবং সার্ভারের আলাদা দায়িত্ব থাকে:
- **Client (Frontend):** ইউজারের সাথে সরাসরি ইন্টারঅ্যাক্ট করে। এটি HTML, CSS এবং JavaScript ব্যবহার করে ব্রাউজারে UI রেন্ডার করে।
- **Server (Backend):** এটি ইউজারের আড়ালে (behind the scenes) কাজ করে। এটি ডেটাবেস ম্যানেজ করে, সিকিউরিটি নিশ্চিত করে, এপিআই (API) হ্যান্ডেল করে এবং ব্যবসায়িক লজিক (Business Logic) প্রসেস করে।

### What is the difference between server-side rendering (SSR) and client-side rendering (CSR)?
| বৈশিষ্ট্য | Server-Side Rendering (SSR) | Client-Side Rendering (CSR) |
|---|---|---|
| **রেন্ডারিং কোথায় হয়** | সার্ভারে পুরো HTML পেজটি তৈরি হয়ে ব্রাউজারে পাঠানো হয়। | সার্ভার শুধু একটি ফাঁকা HTML এবং জাভাস্ক্রিপ্ট বান্ডেল পাঠায়, বাকিটা ব্রাউজারে রেন্ডার হয়। |
| **প্রাথমিক লোড টাইম (First Paint)** | খুব ফাস্ট, কারণ ব্রাউজার রেডিমেড পেজ দেখতে পায়। | কিছুটা স্লো, কারণ ব্রাউজারকে আগে JS ডাউনলোড এবং রান করতে হয়। |
| **SEO ফ্রেন্ডলি** | হ্যাঁ, সার্চ ইঞ্জিন ক্রলার খুব সহজেই পেজের কনটেন্ট রেডি অবস্থায় পেয়ে যায়। | আগে সমস্যা ছিল, তবে আধুনিক ক্রলারগুলো এখন JS রেন্ডার করতে পারে, তবুও SSR এর চেয়ে কঠিন। |
| **সার্ভার লোড** | বেশি থাকে, কারণ রিকোয়েস্ট এলেই সার্ভারকে পেজ জেনারেট করতে হয়। | অনেক কম, কারণ সার্ভার শুধু JSON ডাটা পাঠায়। |

### How does hydration work in modern full-stack frameworks?
**Hydration** হলো এমন একটি প্রক্রিয়া, যেখানে সার্ভার থেকে পাঠানো একটি স্ট্যাটিক HTML পেজকে ব্রাউজারে জাভাস্ক্রিপ্ট ব্যবহার করে ইন্টারঅ্যাক্টিভ (যেমন বাটনে ক্লিক করলে বা ইভেন্ট লিসেনার অ্যাড করে) করা হয়। Next.js বা Nuxt.js এর মতো ফ্রেমওয়ার্কে প্রথমে SSR এর মাধ্যমে দ্রুত স্ট্যাটিক পেজ দেখানো হয় এবং পরে Hydration এর মাধ্যমে পেজটিকে একটি পূর্ণাঙ্গ সিঙ্গেল পেজ অ্যাপ্লিকেশন (SPA) বানিয়ে ফেলা হয়।

## 19. What is the HTTP request-response cycle?
যখন ক্লায়েন্ট সার্ভার থেকে কোনো ডেটা চায়, তখন তাদের মধ্যে যে সাইকেলটি কাজ করে:
1. **Request:** ক্লায়েন্ট একটি HTTP রিকোয়েস্ট (যেমন `GET /users`) তৈরি করে এবং সার্ভারে পাঠায়।
2. **Process:** সার্ভার সেই রিকোয়েস্ট রিসিভ করে, যাচাই করে এবং ডেটাবেস থেকে তথ্য নিয়ে একটি রেসপন্স তৈরি করে।
3. **Response:** সার্ভার HTTP রেসপন্স (স্ট্যাটাস কোড এবং ডেটাসহ) ক্লায়েন্টের কাছে ফেরত পাঠায়।
4. **Render:** ব্রাউজার ডেটা পেয়ে স্ক্রিনে রেন্ডার করে।

### What happens at each layer of the OSI model during an HTTP request?
- **Application Layer:** ব্রাউজার HTTP রিকোয়েস্ট জেনারেট করে (যেমন `GET /index.html`)।
- **Presentation Layer:** ডেটা এনকোড এবং এনক্রিপ্ট (HTTPS/TLS) করা হয়।
- **Session Layer:** সার্ভারের সাথে সেশন ম্যানেজ করা হয়।
- **Transport Layer:** মেসেজটিকে ছোট ছোট অংশে (Segments) ভাগ করে এবং সোর্স ও ডেস্টিনেশন পোর্ট (مثل 80 বা 443) বসানো হয়। TCP প্রোটোকল ব্যবহার করে রিলায়েবিলিটি নিশ্চিত করা হয়।
- **Network Layer:** সেগমেন্টগুলোতে IP অ্যাড্রেস বসিয়ে প্যাকেট তৈরি করা হয়।
- **Data Link Layer:** প্যাকেটগুলোতে MAC অ্যাড্রেস বসিয়ে ফ্রেম তৈরি করা হয়।
- **Physical Layer:** সবশেষে এটিকে ফিজিক্যাল সিগনালে রূপান্তরিত করে ক্যাবলের মাধ্যম দিয়ে রাউটারে পাঠানো হয়।

### How does HTTP keep-alive affect the request-response cycle?
সাধারণত প্রতিটি HTTP রিকোয়েস্টের জন্য সার্ভারের সাথে নতুন করে TCP কানেকশন তৈরি করতে হয়, যা বেশ সময়সাপেক্ষ। **HTTP Keep-Alive** চালু থাকলে, আগের কানেকশনটি সঙ্গে সঙ্গে বন্ধ না হয়ে কিছুক্ষণ খোলা (persistent) থাকে। ফলে ব্রাউজার একই কানেকশন ব্যবহার করে পর পর কয়েকটি রিকোয়েস্ট (যেমন HTML এর পর CSS ও ছবি) পাঠাতে পারে, এতে ল্যাটেন্সি অনেক কমে যায়।

### What is the difference between a "stateless" and "stateful" protocol in this cycle?
- **Stateless:** HTTP হলো একটি স্ট্যাটলেস প্রোটোকল। সার্ভার পরপর করা রিকোয়েস্টগুলোর মধ্যে আগের কোনো রিকোয়েস্টের স্মৃতি বা স্টেট মনে রাখে না। প্রতিটি রিকোয়েস্টকে সম্পূর্ণ নতুন মনে করে।
- **Stateful:** স্টেটফুল প্রোটোকলে (যেমন TCP বা FTP) দুটি পয়েন্টের মধ্যে কানেকশনের শুরু থেকে শেষ পর্যন্ত একে অপরের অবস্থা মনে রাখে এবং ডেটা শেয়ার করে। ওয়েবে স্টেটফুল আচরণ করতে সেশন এবং কুকিজ (Cookies) ব্যবহার করা হয়।

## 20. How do browsers act as clients that request resources from web servers?
ব্রাউজার হলো একটি ক্লায়েন্ট সফটওয়্যার, যা ইউজারের পক্ষে URL রিকোয়েস্ট করে, সার্ভার থেকে HTML/CSS/JS ডাউনলোড করে এবং ব্রাউজার ইঞ্জিনের সাহায্যে স্ক্রিনে তা সুন্দরভাবে উপস্থাপন করে।

### What is the browser's critical rendering path?
**Critical Rendering Path (CRP)** হলো ব্রাউজারের সেই ধারাবাহিক ধাপগুলো, যা সম্পূর্ণ করে সে সার্ভার থেকে পাওয়া ডেটাকে স্ক্রিনে প্রদর্শনযোগ্য পিক্সেলে রূপান্তর করে। এর মূল ধাপগুলো হলো:
1. **DOM Tree Construction:** HTML পার্স করে Document Object Model (DOM) তৈরি।
2. **CSSOM Tree Construction:** CSS পার্স করে CSS Object Model তৈরি।
3. **Render Tree:** DOM এবং CSSOM মিলিয়ে Render Tree তৈরি। রেস্পন্সিভ ডিসপ্লে না হওয়া আইটেম (যেমন `display: none`) রেন্ডার ট্রিতে থাকে না।
4. **Layout:** প্রতিটি উপাদান স্ক্রিনে কোথায় এবং কী সাইজে বসবে তার হিসেব করা।
5. **Paint:** উপাদানগুলোকে স্ক্রিনের পিক্সেলে রঙ দিয়ে ফুটিয়ে তোলা।

### How do browsers handle concurrent requests to the same server?
একটি ব্রাউজার সাধারণত একই ডোমেইন বা সার্ভারের জন্য একসাথে ৬ থেকে ৮ টি প্যারালাল (concurrent) TCP কানেকশন তৈরি করতে পারে (HTTP/1.1 এর ক্ষেত্রে)। 
- যদি একই ডোমেইন থেকে ২০টি ছবি লোড করতে হয়, ব্রাউজার প্রথমে ৬টি রিকোয়েস্ট পাঠায়। সেগুলো শেষ হলে বাকিগুলো পাঠায়। 
- ওয়েব পারফরম্যান্স বাড়াতে ডেভেলপাররা **Domain Sharding** ব্যবহার করে একাধিক সাব-ডোমেইন থেকে অ্যাসেট সার্ভ করতেন।
- তবে **HTTP/2 এবং HTTP/3**-এ একটি সিঙ্গেল কানেকশনের মাধ্যমে অসংখ্য রিকোয়েস্ট মাল্টিপ্লেক্স (Multiplexing) করে পাঠানো যায়, তাই এখন আর এটি কোনো সমস্যা নয়।


## 21. What are web servers and web hosting?
- **Web Server:** এটি হলো ইন্টারনেট সংযুক্ত একটি কম্পিউটার এবং সফটওয়্যার (যেমন Apache বা Nginx), যা ক্লায়েন্ট থেকে আসা HTTP রিকোয়েস্টগুলো গ্রহণ করে এবং ওয়েবসাইটের ফাইল বা ডেটাগুলো ক্লায়েন্টকে সার্ভ করে।
- **Web Hosting:** এটি একটি সার্ভিস, যা ব্যক্তি বা প্রতিষ্ঠানকে ওয়েব সার্ভারে স্টোরেজ বা স্পেস ভাড়া দেয়, যাতে ওয়েবসাইট বা অ্যাপ্লিকেশনটি সার্বক্ষণিক ইন্টারনেটে লাইভ থাকে।

### What is the difference between shared hosting, VPS, and dedicated servers?
| হোস্টিং টাইপ | ব্যাখ্যা | উদাহরণ |
|---|---|---|
| **Shared Hosting** | একটি ফিজিক্যাল সার্ভারের রিসোর্স (CPU, RAM) শত শত ওয়েবসাইটের সাথে শেয়ার করা হয়। | একটি ট্রেন বগির মতো। স্পিড কম হতে পারে, তবে সস্তা। |
| **VPS (Virtual Private Server)** | একটি সার্ভার ভারচুয়ালাইজেশনের মাধ্যমে কয়েকটি ভাগে বিভক্ত করা হয়। এখানে আপনার জন্য নির্দিষ্ট রিসোর্স বরাদ্দ থাকে। | অ্যাপার্টমেন্ট বিল্ডিংয়ের মতো। প্রাইভেসি ও কন্ট্রোল বেশি। |
| **Dedicated Server** | সম্পূর্ণ একটি ফিজিক্যাল সার্ভার მხოლოდ আপনার ওয়েবসাইটের জন্য বরাদ্দ থাকে। এখানে কেউ রিসোর্স শেয়ার করে না। | নিজের প্রাইভেট বাড়ির মতো। সবচেয়ে ফাস্ট এবং ব্যয়বহুল। |

### What is serverless hosting and how does it differ from traditional hosting?
**Serverless Hosting (বা Serverless Computing)** হলো ক্লাউড প্রোভাইডারদের (যেমন AWS Lambda, Vercel) এমন একটি মডেল, যেখানে সার্ভারের ব্যবস্থাপনা বা স্কেলিং নিয়ে ডেভেলপারকে ভাবতে হয় না।
- **পার্থক্য:** ট্র্যাডিশনাল হোস্টিংয়ে সবসময় সার্ভার রানিং রাখতে হয় এবং ট্রাফিক না থাকলেও বিল দিতে হয়। কিন্তু সার্ভারলেস মডেলে অ্যাপ্লিকেশন বা ফাংশন শুধুমাত্র ট্রাফিক এলেই ট্রিগার হয়, এবং আপনি শুধু যতটুকু সময় কোড এক্সিকিউট হয়েছে, তার জন্যই বিল দেবেন (Pay-as-you-go)।

## 22. What are Web servers (Apache, Nginx), Client-side vs Server-side, Request headers, and Response codes?
ওয়েব সার্ভার মূলত দুটি প্রধান সফটওয়্যার দ্বারা চালিত হয়: **Apache** (যা বেশ পুরোনো এবং অনেক মডিউল সাপোর্ট করে) এবং **Nginx** (যা ইভেন্ট-ড্রিভেন এবং হাই পারফরম্যান্স নিয়ে কাজ করে)। 
- **Request Headers:** ক্লায়েন্ট সার্ভারকে তার ব্রাউজার, ডিভাইসের ধরন, কুকিজ এবং সিকিউরিটি নিয়ে কিছু মেটা-ডেটা পাঠায়।
- **Response Headers & Codes:** সার্ভার তার স্ট্যাটাস কোড (যেমন ২০০, ৪০৪) এবং কনটেন্টের ধরন হেডার হিসেবে পাঠায়।

### What are the most important HTTP request headers a backend developer should know?
ব্যাকএন্ড ডেভেলপারদের নিচে দেওয়া হেডারগুলো ভালোভাবে বুঝতে হয়:
- `Authorization:` এপিআই কলের সময় বিয়ারার টোকেন (JWT) পাঠাতে লাগে।
- `Accept:` ক্লায়েন্ট কী ধরণের ফাইল (JSON, HTML) গ্রহণ করতে পারবে তা জানায়।
- `Content-Type:` ক্লায়েন্ট সার্ভারে কী ধরণের ডেটা পাঠাচ্ছে (যেমন `application/json`), তার ডিক্লারেশন।
- `User-Agent:` ইউজারের ব্রাউজার এবং ওএস এর বিস্তারিত তথ্য থাকে।
- `Host:` ক্লায়েন্ট কোন ডোমেইনকে অ্যাক্সেস করতে চাচ্ছে।

### How do custom response headers improve security (e.g., CSP, HSTS)?
সার্ভার রেসপন্সে সিকিউরিটি হেডার বসিয়ে অ্যাপকে সুরক্ষিত রাখা যায়:
- **CSP (Content Security Policy):** এটি বলে দেয় যে ব্রাউজার কোন কোন ডোমেইন থেকে স্ক্রিপ্ট, ছবি বা সিএসএস লোড করতে পারবে। এটি XSS আক্রমণ রোধ করে।
- **HSTS (HTTP Strict Transport Security):** ব্রাউজারকে বাধ্য করে যেন শুধু `https://` দ্বারাই ওয়েবসাইটে ঢোকা যায়, কোনো অবস্থাতেই যেন `http://` দিয়ে অ্যাক্সেস না হয়।
- **X-Frame-Options:** ওয়েবসাইটটি যেন অন্য ওয়েবসাইটের আড়ালে আইফ্রেম (iframe) হিসেবে লোড হতে না পারে তা নিশ্চিত করে (Clickjacking রোধ করে)।

## 23. What is a Content Delivery Network (CDN), and how does it improve website performance?
**CDN (Content Delivery Network)** হলো বিশ্বব্যাপী ছড়িয়ে থাকা প্রক্সি সার্ভার বা ডেটা সেন্টারের একটি সিস্টেম।
- যদি আপনার মূল সার্ভার আমেরিকায় থাকে, তবে বাংলাদেশ বা সার্ভার থেকে দূরে অবস্থান করা কোনো ইউজারের সাইট লোড হতে অনেক সময় লাগবে। 
- CDN আপনার সাইটের স্ট্যাটিক কনটেন্টগুলো (ছবি, সিএসএস, জেএস) বিশ্বের বিভিন্ন স্থানে (যেমন ইন্ডিয়া বা সিঙ্গাপুরে) ক্যাশ করে রাখে। ফলে ইউজার যখন রিকোয়েস্ট করে, তখন তার সবচেয়ে কাছের CDN নোড বা "Edge Server" থেকে ডেটা সার্ভ করা হয়। এতে পারফরম্যান্স এবং স্পিড উল্লেখযোগ্যহারে বৃদ্ধি পায়।

### What is the difference between a pull CDN and a push CDN?
| বৈশিষ্ট্য | Pull CDN | Push CDN |
|---|---|---|
| **কীভাবে কাজ করে?** | যখন কোনো ইউজার প্রথমবার રিকোয়েস্ট করে, তখন CDN মূল সার্ভার থেকে ডেটা "টেনে" (pull) এনে নিজের কাছে রাখে এবং ইউজারকে দেয়। | ব্যাকএন্ড ডেভেলপার আপডেট করার সাথে সাথেই মূল সার্ভার থেকে ডেটা CDN-এ সরাসরি "ঠেলে" (push) পাঠিয়ে দেওয়া হয়। |
| **উপযোগিতা** | যেসব ওয়েবসাইটে প্রচুর ট্রাফিক থাকে এবং হাজার হাজার ছোট ফাইল থাকে, সেখানে ফাস্ট সেটআপের জন্য এটি দারুণ। | যেখানে ট্রাফিক কম, ফাইল সাইজ বড় বা যে কনটেন্টগুলো কদাচিৎ পরিবর্তন হয়, সেখানে এটি কাজে দেয়। |

### How does cache invalidation work in a CDN?
CDN-এ একবার ফাইল রেখে দিলে সেটি নির্দিষ্ট সময় পর্যন্ত (TTL) স্টোর হয়ে থাকে। কিন্তু ডেভেলপার যদি ওই ফাইলটি আপডেট করেন, তখন ইউজাররা আগের ফাইলটি দেখতে থাকে। এর সমাধানে **Cache Invalidation (বা Purge / Eviction)** করা হয়, যার মাধ্যমে CDN থেকে জোরপূর্বক পুরোনো ফাইলটি মুছে দেওয়া হয় যাতে CDN আবার মূল সার্ভার থেকে নতুন আপডেট করা ফাইলটি ফেচ করতে বাধ্য হয়।

### What is "Edge Computing" and how does it relate to CDNs?
সাধারণত সব ধরনের প্রসেসিং বা কোড রান করানো হয় মূল সার্ভারে (Origin Server)। কিন্তু **Edge Computing** হলো সেই কনসেপ্ট যেখানে কাস্টম ফাংশন বা কিছু ব্যাকএন্ড লজিক (যেমন ইউজারের অথেন্টিকেশন বা রিডাইরেক্ট) ইউজারদের একদম কাছের বা "Edge" এ থাকা CDN সার্ভারে রান করা হয়। 
- Cloudflare Workers, AWS Lambda@Edge হলো এর উদাহরণ। এটি সার্ভারের চাপ একেবারেই কমিয়ে দেয় এবং ইউজারকে ন্যানোসেকেন্ডে রেসপন্স দিতে পারে।


## 24. What is the role of load balancers in managing server traffic?
**Load Balancer (লোড ব্যালেন্সার)** হলো এমন একটি ডিভাইস বা সফটওয়্যার যা ইউজারের রিকোয়েস্ট এবং সার্ভারগুলোর মাঝখানে ট্রাফিক পুলিশের মতো দাঁড়িয়ে থাকে। একটি অতিরিক্ত ভিজিটর বা হাই ট্রাফিক সাইটে, রিকোয়েস্টগুলো কোনো একটি সলিড সার্ভারে না পাঠিয়ে, লোড ব্যালেন্সার সেটি একাধিক সার্ভারের মাঝে সমানভাবে বা নির্দিষ্ট নিয়মে ভাগ (distribute) করে দেয়। এতে কোনো একটি সার্ভার ওভারলোড বা ক্র্যাশ হওয়া থেকে রক্ষা পায় এবং অ্যাপ্লিকেশনটি সার্বক্ষণিক সচল (highly available) থাকে।

### What are the differences between Layer 4 and Layer 7 load balancing?
লোড ব্যালেন্সিং OSI মডেলের নির্দিষ্ট লেয়ারে কাজ করে।
- **Layer 4 (Transport Layer):** এই ব্যালেন্সার শুধুমাত্র IP অ্যাড্রেস এবং পোর্ট নাম্বারের (যেমন TCP/UDP) ওপর ভিত্তি করে ট্রাফিক ডিস্ট্রিবিউট করে। এটি রিকোয়েস্টের ভেতরে থাকা ডেটা বা পে-লোড (Payload) পড়ে না। এটি খুব ফাস্ট এবং সিম্পল।
- **Layer 7 (Application Layer):** এটি আরও বেশি স্মার্ট। এটি HTTP হেডার, কুকি, URL এর পাথ (যেমন `/video` অথবা `/image`) পড়ে পুরো রিকোয়েস্টের কনটেন্ট বুঝতে পারে। এর ফলে আপনি ইমেজের ট্রাফিক ইমেজ সার্ভারে এবং ভিডিওর ট্রাফিক ভিডিও সার্ভারে আলাদা করে পাঠাতে পারেন।

### What load balancing algorithms are commonly used (round robin, least connections, IP hash)?
লোড ব্যালেন্সাররা বিভিন্ন অ্যালগরিদম ব্যবহার করে ট্রাফিক ডিস্ট্রিবিউট করে:
- **Round Robin:** খুব সিম্পল। প্রথম রিকোয়েস্ট সার্ভার-১ এ, দ্বিতীয়টি সার্ভার-২ এ, তৃতীয়টি সার্ভার-৩ এ.. এভাবে সাইক্লিক আকারে ঘুরতে থাকে।
- **Least Connections:** যেই সার্ভারের সাথে বর্তমানে সবচেয়ে কম ক্লায়েন্ট কানেক্টেড আছে বা যেই সার্ভারটি সবচেয়ে বেশি ফ্রি, তাকে রিকোয়েস্ট দেওয়া হয়।
- **IP Hash:** ক্লায়েন্টের IP অ্যাড্রেসটিকে হ্যাশ (Hash) করে নির্ধারণ করা হয় কোন সার্ভারের কাছে রিকোয়েস্ট পাঠাতে হবে। এর সুবিধা হচ্ছে, একজন ব্যবহারকারী সবসময় নির্দিষ্ট একটি সার্ভারে যায়, যা স্ট্যাট বা সেশন (Session) সংরক্ষণের জন্য বেশ গুরুত্বপূর্ণ।

## 25. What are reverse proxies, and how do they enhance backend server performance? 
**Reverse Proxy** হলো এমন একটি সার্ভার, যা মূল ব্যাকএন্ড সার্ভারের সামনে বসে ক্লায়েন্ট থেকে আসা রিকোয়েস্টগুলোকে গ্রহণ করে। ক্লায়েন্ট কখনো ডিরেক্ট ব্যাকএন্ড সার্ভারের আইপি জানতে পারে না, তারা মনে করে রিভার্স প্রক্সিটিই মূল সার্ভার।
- **নিরাপত্তা প্রদান:** ব্যাকএন্ড সার্ভারের আসল আইপি লুকিয়ে রাখে, ফলে ডিরেক্ট হ্যাকিং থেকে রক্ষা পায়।
- **ক্যাশিং:** রিভার্স প্রক্সি প্রায়শই ডাইনামিক ডেটা বা ভারী রিপিট হওয়া রেসপন্স ক্যাশ করে রাখে যেন ব্যাকএন্ডকে কষ্ট করতে না হয়। 
- **কম্প্রেশন:** ব্যাকএন্ড টিমের পাঠানো ফাইলকে গিজিপ (Gzip/Brotli) কম্প্রেস করে ইউজারকে দেয়, এতে লোডিং টাইম অনেক কমে যায়।

### What is the difference between a reverse proxy and a forward proxy?
| প্রক্সি টাইপ | কার জন্য কাজ করে? | উদাহরণ / কাজ |
|---|---|---|
| **Forward Proxy** | ক্লায়েন্টের (ইউজারের) জন্য। | আপনার অফিস বা স্কুলের প্রক্সি, যা আপনি ইন্টারনেটে কোথায় যাচ্ছেন তা নিয়ন্ত্রণ এবং ফিল্টার করে। ইন্টারনেট কখনোই জানতে পারে না আসল ইউজার কে (অনেকটা VPN এর মত)। |
| **Reverse Proxy** | সার্ভারের জন্য। | ব্যাকএন্ড সার্ভারের সামনে বসে ক্লায়েন্টের রিকোয়েস্টগুলো গ্রহণ করে এবং সার্ভার থেকে ডেটা এনে ক্লায়েন্টকে দেয়। ইউজার কখনোই জানতে পারে না পেছনের আসল সার্ভার কোনটি। |

### How does Nginx function as both a reverse proxy and a web server?
Nginx একই সাথে চমৎকার ওয়েব সার্ভার এবং রিভার্স প্রক্সি হিসেবে কাজ করতে পারে:
- **ওয়েব সার্ভার হিসেবে:** এটি ডিস্ক থেকে সরাসরি স্ট্যাটিক ফাইল (HTML, CSS, Image) সার্ভ করতে পারে।
- **রিভার্স প্রক্সি হিসেবে:** যখন ইউজারের কোনো ডায়নামিক বা এপিআই (API) রিকোয়েস্ট আসে, Nginx সেটি রিসিভ করে পেছনের Node.js বা Python সার্ভারের কাছে ফরোওয়ার্ড করে দেয় এবং তাদের থেকে পাওয়া রেসপন্সগুলো ইউজারের কাছে ফেরত পাঠায়।

### How do reverse proxies help with SSL termination and caching?
- **SSL Termination:** HTTPS কানেকশনগুলো প্রসেস এনক্রিপ্ট বা ডিক্রিপ্ট করতে প্রচুর CPU পাওয়ার দরকার হয়। রিভার্স প্রক্সি (যেমন Nginx, HAProxy) এই এনক্রিপশন কাজের দায়িত্ব নেয়। প্রক্সি পর্যন্ত ক্লায়েন্ট এবং প্রক্সির মধ্যে HTTPS থাকে, আর প্রক্সি থেকে ব্যাকেন্ড সার্ভারে কমিউনিকেশন সাধারণ HTTP-তে হয়। এর ফলে ব্যাকেন্ড সার্ভারগুলো শুধু ডেটা প্রসেসিংয়ে ফোকাস করতে পারে।

## 26. How do backend developers choose between Apache and Nginx for specific use cases? 
ডেভেলপাররা সাধারণত তাদের প্রজেক্টের সাইজ, ট্রাফিকের ধরণ এবং ল্যাঙ্গুয়েজ ইকোসিস্টেমের উপর ভিত্তি করে নির্বাচন করেন।
- **Apache** এর আর্কিটেকচার অনেকটা প্রসেস-ড্রিভেন। কোনো রিকোয়েস্ট আসলে এটি নতুন থ্রেড তৈরি করে বা আগে থেকে তৈরি করা থ্রেড ব্যবহার করে। ডাইনামিক পেজগুলোতে এটি খুব ভালো কাজ করে।
- **Nginx** ইভেন্ট-ড্রিভেন আর্কিটেকচারে চলে, তাই এটি থ্রেড ব্লক না করে একসাথে প্রচুর কানেকশন হ্যান্ডেল করতে পারে এবং স্ট্যাটিক কন্টেন্ট ডেলিভারি বা প্রক্সি হিসেবে এর তুলনা হয় না। 

### What is the difference in how Apache and Nginx handle concurrent connections?
- **Apache (Thread-based):** যখন প্রচুর রিকোয়েস্ট আসে, Apache প্রতিটি রিকোয়েস্টের জন্য একটি করে নির্দিষ্ট থ্রেড এসাইন করে। এর ফলে অনেক ট্রাফিক আসলে মেমোরি খরচ বেড়ে সার্ভার ডাউন হয়ে যাওয়ার সম্ভাবনা থাকে (C10K problem)।
- **Nginx (Event-Driven / Asynchronous):** এটি একটি মাত্র প্রসেসের ভেতর হাজার হাজার রিকোয়েস্ট বা ইভেন্ট লুপের মাধ্যমে হ্যান্ডেল করতে পারে। রিকোয়েস্ট প্রসেসিং না হওয়া পর্যন্ত সে মেমোরি ব্লক করে বসে থাকে না। এজন্য মেমোরি অনেক সাশ্রয় হয়।

### When would you choose a cloud load balancer (e.g., AWS ALB) over Nginx?
- আপনি যদি সার্ভার ম্যানেজমেন্ট এর ঝামেলায় যেতে না চান (Managed service)।
- যখন আপনার ক্লাউডে Auto-scaling এর দরকার হয় (যেমন AWS এ EC2 ইন্সটেন্স বাড়লে ALB অটোমেটিক সেগুলো রিড করে ট্রাফিক পাঠাতে পারে)।
- ক্লাউড প্রোভাইডারের অন্যান্য সার্ভিসের (যেমন WAF, Route53, Certificate Manager) সাথে খুব সহজেই নেটিভভাবে ইন্টিগ্রেশনের প্রয়োজন হলে AWS Application Load Balancer (ALB) বেস্ট চয়েজ হতে পারে। 
- অন্যদিকে, আপনার যদি বাজেট কম থাকে বা কাস্টম রাউটিং রুল লেখার দরকার হয় বা অন-প্রেমিস (On-premise) সার্ভার থাকে, সে ক্ষেত্রে Nginx দিয়ে লোড ব্যালেন্সার বসানো হয়।
